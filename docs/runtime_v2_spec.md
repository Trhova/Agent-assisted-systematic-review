# Runtime infrastructure revision 2

Recorded 2026-10-12 before the new full diabetes execution. This changes infrastructure, not the frozen eligibility, outcomes, statistical estimator or published reference answers. Original observations remain under `data/benchmarks/runs`; the new execution uses `data/benchmarks/runtime_v2`.

## Acquisition

Discovery reads only independently retrieved record identifiers and bibliographic metadata. It follows indexed free links, public OpenAlex repository locations, Semantic Scholar open-access locations, Crossref full-text/publisher links, DOI redirects and publisher PDF metadata. It never searches a benchmark answer file. Sources are public requests without authentication bypass. First-page DOI or normalized title identity must match before a PDF is accepted; bibliographic citations on later pages cannot establish identity.

Defaults per discovery or PMC retrieval operation: at most 12 network requests including redirects, 20 MB per response, 120 seconds checked between requests/chunks, and at most four requests in a redirect chain. Connect/read inactivity timeouts apply. OS DNS stalls cannot be interrupted by this requests-based bound. Responses have checksums and durable journals; confirmed failures have a negative cache, and HTTP 429 creates a shared host cooldown. No API subscriptions, paid downloads or credit purchases are configured. Public access does not assert a redistribution license. JATS, PMC and alternative discovery are separate bounded operations, so this is not a single aggregate 120-second cap over every stage of a record. Optional existing `OPENALEX_API_KEY` and `SEMANTIC_SCHOLAR_API_KEY` values are sent only to their exact provider hosts, never carried through publisher redirects or written to request journals; neither was present during the observed checks.

Official interfaces: [Crossref full-text metadata](https://www.crossref.org/documentation/retrieve-metadata/text-and-data-mining/), [OpenAlex authentication](https://help.openalex.org/api/authentication/), [Semantic Scholar API](https://api.semanticscholar.org/api-docs/). A free optional service key may improve rate limits, but the current path uses anonymous public access and records failures.

## Large documents

Sources above 400,000 characters enter discovery segmentation rather than numeric extraction. Segments contain at most 60,000 characters with 3,000-character overlap, exact original offsets and source/segment hashes. Every original character is covered. The complete source remains preserved.

Each segment is conservatively screened for candidate trial reports. Candidate titles and evidence must be literal source text; one bounded correction is allowed. Unsupported candidates remain unresolved. Exact duplicate title/evidence pairs merge only their provenance locations, not assumed trial identities. Collection entries are not pooled as independent studies.

Candidate titles can be resolved through Europe PMC to a unique exact normalized bibliographic title. Resolved records enter a separately logged supplemental screening queue with the original eligibility. Unmatched/ambiguous entries remain unresolved. The default per-record batch is 24 new segments; the CLI continues unfinished segmentation for at most three rounds and stops on no progress. This is bounded, restartable execution, not an unbounded background service.

## Participant dependence

Before pooling, every accepted report pair receives source-backed relationship assessment and a separate verification call. Complete paired sources must fit the input bound; at most 64 report pairs are assessed per pass. Unassessed or unsupported pair relationships are unresolved, not presumed independent.

Registry aliases normalize, exact repeat comparisons can be deduplicated while preserving all report IDs, and discordant reports from the same trial cannot be selected automatically. Different registry numbers alone do not prove distinct participants. Conflicting source adjudication and registry identity block the involved rows. Multiarm shared controls require an explicit source-supported arm identity; no implicit split or arbitrary active-arm selection is implemented. A prespecified extension is still needed to combine eligible active arms or model dependent effects.

## Integrated suite and source-checked RoB2 drafts

It preserves separate suite attempts, does not evaluate stale outputs after a failed launcher, and can evaluate a map of already-finished runs without model calls. The integrated live warm run is under `data/benchmarks/final_suite_v1`; old observations are unchanged.

The draft stage reuses `protocol/schemas/rob2.schema.json`, `protocol/prompts/rob2.md`, and the repository's abbreviated `ROB_protocols` templates. The separate `rob2_draft_v1` audit policy fixes the effect of interest to assignment and the actual extracted outcome/timepoint; it does not change any numerical benchmark definition, exclusion, effect or weight. Only supplied original-report text and retrieved attachments may support judgments. Cited protocols/registries are not represented as accessed external sources. Exact snippets, overall/domain consistency, one bounded repair and an independent model check constrain the drafts. Unverified drafts remain visible. The [Cochrane handbook](https://www.cochrane.org/authors/handbooks-and-manuals/handbook/current/chapter-08) describes outcome-specific RoB2 assessments and the distinction between assignment and adherence effects. This implementation does not claim full canonical algorithm implementation, expert validation or certainty-of-evidence grading.

Draft assets, code hash, request hashes, full signaling answers, failed checks and prior attempts are retained. The final review export labels the ratings as automated drafts. Suite launching/comparison separation and failure handling have tests; the live integrated suite exercises the actual authenticated model calls. The numeric rerun uses validated development caches and is not a fresh held-out evaluation.

Resume context is now explicitly bound to protocol hash, backend and model. The validated input-copy helper carries this identity; changing it requires a fresh work directory. This prevents attributing old cached screening decisions to a newly requested model. These guards and the suite/draft modules were added after the revision-9 Ma/revision-10 Li numerical snapshot; the integrated suite records its newer code hash separately.
